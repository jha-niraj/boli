1. What "document intelligence" is

Document intelligence (also called document AI, document understanding or "doc digitisation") is turning a picture of a document into data a program can use. The input is a photo, a scan or a PDF. The output is text, structure (headings, tables), and named fields like "amount due". Sarvam sells this today as Sarvam Vision / Document AI: a 3B-parameter model for 23 languages, async jobs, output as Markdown or HTML plus page-level JSON, at most 10 pages per PDF.

It is not one task. It is a stack of smaller tasks, and every product in this space is some mix of them:

Sub-taskPlain meaningOn our electricity bill
OCR (optical character recognition)Turn pixels of letters into characters you can copy.The shape "राम" becomes the three Unicode characters र, ा, म.
Layout analysisFind the regions on a page and label them: title, paragraph, table, stamp, photo, signature. Each region is a bounding box (x, y, width, height in pixels).The title band, the label/value block, the red seal.
Reading orderDecide which region comes first. Two-column notices and forms break naive left-to-right reading.Label then value, row by row; the seal is read last.
Table structureRebuild rows, columns and merged cells, not just the words inside.A tariff slab table: units 0-20, 21-30, and so on.
Key-value extractionFill a fixed set of named fields (a schema) from the page.amount_paisa = 124000.
ClassificationSay what kind of document this is, so the right schema is used."electricity_bill", not "citizenship_card".
Handwriting (HTR)OCR for handwritten text: much harder, more varied.A meter reader's pen note in the margin.
Document VQA (visual question answering)Answer a question about the page: "When is this due?""२०८२ मंसिर १५".
Summary / translationRun a normal language model on the extracted text."Electricity bill for Kartik, Rs 1,240, due 15 Mangsir." in English.

The last row matters for planning: once you have good text, summaries, translation and Q&A are ordinary chat tasks. Boli already serves a chat model, so the new, hard part is the reading, not the writing.

2. Two ways to build it

There are two architectures. Architecture here just means "which pieces, connected how".

(a) Classic pipeline(b) End-to-end VLM
StrengthsExact bounding boxes for every word; small, fast, runs on CPU; each stage can be swapped and tested alone.One model, one call; understands context ("this number is the total because it is next to जम्मा"); handles odd layouts, stamps, photos of crumpled paper; can answer questions.
WeaknessesMany moving parts; errors chain; old OCR engines struggle on Devanagari conjuncts and real scans.Needs a GPU for speed; can hallucinate (write plausible text that is not on the page) or loop; boxes are rough unless the model was trained to output them.
Fits Boli?As a helper (layout boxes for the playground preview, a cheap first OCR pass).Yes, as the core. Boli already runs llama-server, which accepts images once the mmproj is loaded.

Two open "frameworks" wrap these ideas so you do not wire them by hand: Docling (IBM, MIT licence; PDF parsing, layout, tables, plug-in OCR, and a VLM mode with granite-docling) and MinerU (OpenDataLab; its MinerU2.5-Pro model is 1.2B, Apache 2.0 with additional terms). They are useful to study and to compare against, but both are tuned mostly on English and Chinese.

Check yourself

A government notice has two columns. Which sub-task decides that the left column is read fully before the right one?

Reading order sorts the regions that layout analysis found. OCR only turns each region's pixels into characters.

Why is a VLM usually better than "OCR then LLM" at picking the right number as the total?

The LLM in a pipeline only gets a flat string; the VLM sees where the number sits. It can still hallucinate, which is why we validate in code.

3. Inside a vision-language model

A VLM (vision-language model) is a normal language model, like the Gemma 4 E4B Boli already serves, with an extra front door for pictures. The language model only understands tokens (numbered pieces of text, each turned into a long list of numbers called a vector). So the picture must be turned into vectors that look like tokens. That is all the extra parts do.

PatchA small square tile cut from the image, the visual equivalent of a word piece.
Vision encoderA neural network (usually a ViT, "vision transformer") that turns each patch into a vector describing what it shows.
ProjectorA small layer that translates encoder vectors into the exact vector "language" the LLM expects. Short for multimodal projector, hence mmproj.
Token budgetHow many image tokens one picture becomes. A page at 1120 tokens costs about as much prefill as 1,120 words of prompt.
Prefill vs decodePrefill reads the input (image + prompt, fast, measured 130-680 tokens/s on the M5). Decode writes the output (slow, 25-35 tokens/s). A full page of text out is the slow part.
HallucinationThe model writes something plausible that is not on the page. For documents this is the main danger, so we validate fields in code.

A worked time estimate on the M5 Mac: one page at 1120 image tokens is about 2-8 seconds of prefill; writing 600 tokens of Markdown at ~30 tokens/s is about 20 seconds. So one dense page takes roughly half a minute on the Mac, and a 10-page PDF several minutes. That is why PDFs become background jobs (section 6), and why a GPU host matters for this product more than for chat.

Check yourself

Boli's server runs with --no-mmproj. What is missing as a result?

The mmproj GGUF carries the encoder and projector. The language weights are in the main GGUF and are already loaded.

A tiny-print Nepali form reads badly. Which change is most likely to help first, before any fine-tuning?

Detail lost when the image is squeezed into few tokens cannot be recovered by the language model. More tokens and a cleaner scan keep the conjuncts readable.

The honest picture. No open model has published Nepali document scores. A June 2026 Devanagari stress test found every system scores 91-98 chrF++ on clean computer-rendered text, but on 300 real printed scans the field spread across 76 points: the best closed model scored 86.3, a classic engine fell from 93.6 to 58.3, and olmOCR-7B scored 40.5. Shortlist for the bake-off: Gemma 4 E4B (free to try, already deployed), Gemma 4 31B or 26B A4B (same API, bigger), Qwen3-VL-8B and 32B (strong readers), and PaddleOCR-VL 1.6 (the specialist with Nepali on its list and real boxes). Sarvam's own API can be a scoring reference in the test (the repo already has @repo/sarvamai digitiseDocument), but never runs behind Boli's product.

5. Nepali and Devanagari specifics

Why Devanagari is harder to read than English

  • Conjuncts (संयुक्ताक्षर): two or more consonants fused into one shape, e.g. क्ष, त्र, ज्ञ, द्ध, श्र, ह्म. The shape on paper does not look like its parts, and one wrong stroke changes the word.
  • Matras (vowel signs) sit above, below, before or after the consonant: in कि the ि is drawn before क but stored after it in Unicode. Models that read in pixel order get this wrong.
  • Halant (्) and the shirorekha (the top line joining letters) make word and letter boundaries fuzzy for line-based OCR.
  • Unicode normalisation: the same visible word can be stored as different code-point sequences. Always normalise to NFC before comparing or storing, or your accuracy numbers and searches lie.

The Preeti trap (the big Nepal-only one)

Many Nepali government PDFs and old Word files were typed in legacy fonts such as Preeti, Kantipur or Sagarmatha. These fonts draw Devanagari shapes on top of plain English keyboard letters. On screen you see नेपाल; the file actually stores g]kfn. Copy the text, or extract it with a PDF library, and you get gibberish that looks like a working text layer.

What the PDF showsWhat text extraction returnsAfter a Preeti converter
नेपालg]kfnनेपाल

How to handle it in the pipeline:

  1. Detect: the PDF's font list names Preeti / Kantipur / Sagarmatha, or the extracted text is mostly ASCII but the document is supposed to be Nepali, or a Devanagari-character ratio check fails.
  2. Either convert the text with a mapping library (Python: nepali-converter handles Preeti, Kantipur, Sagarmatha, Himalb and has a PDF rescue function; npttf2utf; nepali_unicoder handles reordering like the reph and the ि matra). Converters need fixes for edge cases, so check the output.
  3. Or ignore the text layer and treat the page as an image: render it and let the VLM read the pixels. This sidesteps the font problem completely and is the safer default for a v1.

Digits, dates and money

  • Nepali digits ० १ २ ३ ४ ५ ६ ७ ८ ९ map one-to-one to 0-9. Ask the model to copy what it sees, then convert in code. Do not ask the model to "convert to English digits" while reading; one job per step is more reliable.
  • Bikram Sambat (BS) dates, e.g. २०८२/०८/१५ = BS 2082 month 8 (Mangsir) day 15. BS months have 29 to 32 days that change year to year, so BS to AD is a lookup table, never arithmetic and never the model's guess. Boli already has @repo/calendar with Bikram Sambat support; return both due_date_bs and due_date_ad.
  • Money: रु. १,२४०.००. Indian-style grouping (1,00,000 = one lakh). Store as integer paisa (124000), per Boli's money rule.
  • Mixed script: forms often mix English labels with Nepali values, or Romanized names. Keep the original script in the transcription; add transliteration only as an extra field.
Privacy. Citizenship cards (नागरिकता) carry national ID numbers, photos and family names. Decide before launch: how long uploaded files stay in R2 (for example, deleted 24 hours after the job ends), that customer documents are never used for training without written consent, and that logs never contain extracted fields.

Check yourself

You extract text from a Nepali notice PDF and get ;"rgf-style strings. What is going on?

No OCR ran at all: the file has a text layer, but it is ASCII drawn with a Devanagari-looking font.

Who should convert २०८२/०८/१५ to an AD date?

BS month lengths vary by year; models guess. The model copies the BS date; @repo/calendar converts it, and the API returns both.

6. How it runs on Boli

Two doors into the same reading engine:

  • Simple door: the chat endpoint Boli already has. POST /v1/chat/completions with an image_url part. Good for one image and a quick answer. Developers already know this shape from OpenAI.
  • Document door: a new /v1/documents job API. For PDFs and anything slower than a few seconds. Upload, get a job id, poll for status, fetch the result. This is the same shape Sarvam uses (create job, poll, download).

Why two model passes (Read, then Extract)

Asking for perfect JSON straight from pixels mixes two jobs. Splitting them gives you: a faithful Markdown transcription you can store, search, summarise, translate and answer questions over; a second, short pass that fills the schema while looking at both the image and that Markdown; and a place to check one against the other (every extracted value should appear in the transcription). For a single small image, one combined pass is fine.

Forcing the shape: JSON schema

A JSON schema is a description of the exact fields and types you want. llama-server turns it into a grammar (a rule set that only lets the model pick tokens that keep the output valid), so the reply always parses. It accepts the OpenAI form on the chat endpoint: response_format: {"type": "json_schema", "json_schema": {"schema": {...}}}. Note from the llama.cpp source: the strict flag is ignored and the schema is always applied. vLLM has the same feature (guided decoding). Valid JSON is not the same as correct values: keep the code checks.

Metering

Chat-with-image stays per token. Documents are easiest to understand per page: credits reserved at submit (pages x price), the real amount charged per finished page, the rest released; a failed page is not charged. Set the price from a measured number: cost per page = GPU cost per hour / pages per hour. Illustration only, not a measurement: a GPU rented at Rs 150 per hour that finishes 600 pages per hour costs Rs 0.25 per page, so a price near Rs 0.75 to 1 leaves room. For scale, Sarvam's page lists Rs 1.50 per page for digitisation (check their pricing page). Store prices as integer micro-credits like the rest of Boli.

The playground page in the dashboard

  • Left: drop a file, pick a document type or paste a schema, choose outputs, "Run".
  • Right, three tabs: Preview (the page image with boxes drawn over regions or fields; click a field to highlight its box), JSON (fields, with a warning chip when a check fails), Code (curl / Python / JavaScript for the exact same request, with YOUR_API_KEY).
  • For PDFs, the browser can render page thumbnails itself with pdf.js, so the preview does not wait for the job.
  • Boxes: PaddleOCR-VL and dots.ocr return layout boxes; Gemma 4 lists "object detection" and "pointing" and can be asked for coordinates, but treat those as approximate until measured. A v1 can ship without boxes.

Storage and where each piece runs

  • R2 (Cloudflare's file storage): the uploaded file and the result, saved as keys (*Key columns), served through signed URLs.
  • PDF to images: Boli's @repo/pdf uses unpdf for text, and unpdf's own docs say Workers cannot render pages (no canvas). So rendering runs on the inference node (pdftoppm -r 200 -png from Poppler), or in the browser for the playground.
  • Text-layer shortcut: if @repo/pdf finds a real Unicode text layer (not Preeti), the Read step can use it directly and only Extract needs the VLM. Cheaper and exact.

Check yourself

A customer uploads a 12-page scanned PDF. Where does the model work happen?

Minutes of work that must survive a closed tab and retry a failed page is exactly Boli's "long job" rule. waitUntil is capped at 30 seconds with no retry.

The JSON schema guarantees that...

The grammar only constrains shape. A wrong amount in a valid number field is still wrong, so cross-checks (readings vs units, values present in the transcription) stay.

7. Measuring quality

You cannot pick a model, a token budget or a price without numbers on your documents. The method mirrors docs/inference/02-choose-a-model.md: fix everything but the model, score blind, keep the scripts.

The metrics

CER (character error rate)(substitutions + deletions + insertions) / characters in the correct text. 0.05 = 5 wrong per 100. For Devanagari, count after NFC normalisation, and also report it per grapheme cluster (what a reader sees as one letter, e.g. क्ष).
WER (word error rate)The same at word level. Harsher: one wrong matra makes the whole word wrong. Old Hindi/Marathi OCR baselines sit near 35% WER.
Field accuracyPer field: exact match after normalising (digits, spaces, NFC). Report per field ("amount right 97%") and per document ("all fields right 81%").
Hallucination rateShare of extracted values that do not appear on the page at all. The one to watch most.
Speed and costSeconds per page and pages per GPU-hour, which become the price.

Build a small Nepali test set first

  1. 80 to 150 pages, split by type: electricity / water / internet bills, bank and government forms, notices (including Preeti PDFs), receipts, a few handwritten pages, and ID-card look-alikes made with consent or synthetic data.
  2. Split by quality: clean PDF, flatbed scan, phone photo (angle, shadow), faded or stamped.
  3. For each page write the ground truth: the exact text (NFC) and the correct JSON. This is slow, careful human work; budget a few days with a native reader.
  4. Freeze it. Never tune prompts on the test pages themselves; keep a separate "dev" set for that.
  5. Public extras exist (for example a Nepali Devanagari printed-text OCR eval set on Hugging Face), but real Nepali bills and forms are what customers will send.

When fine-tuning is needed

Fine-tuning means continuing a model's training on your own labelled examples so it learns your documents. Do it only when all of these are true:

  • The error is consistent (same conjuncts, same form type, handwriting), not random.
  • Higher image token budget, better prompt and a bigger model (E4B -> 26B/31B -> Qwen3-VL-32B) did not fix it.
  • You have, or can make, roughly 1,000 to 5,000 labelled pages of that kind. Synthetic pages help: render real Nepali text in many Unicode and legacy fonts, add noise, blur, stamps and rotation.

Then a LoRA fine-tune (training small add-on weights instead of the whole model) on the chosen VLM, the same test set before and after, and a new model name behind the same API, exactly as planned for chat (boli-chat-v1 -> v2).

Check yourself

Model A has 3% CER, model B 4% CER. A invents a total on 2 of 100 bills; B never does. Which do you ship for bills?

CER measures copying; customers act on fields. Field accuracy and hallucination rate decide extraction products.

2. Build the request in a file (a base64 image is too long for a shell argument), then curl it.

python3 - bill.jpg > req.json <<'EOF'
import base64, json, sys
img = base64.b64encode(open(sys.argv[1], "rb").read()).decode()
print(json.dumps({
  "messages": [{"role": "user", "content": [
    {"type": "image_url", "image_url": {"url": f"data:image/jpeg;base64,{img}"}},
    {"type": "text", "text": "Transcribe this document exactly as written, in Markdown. "

  "chat_template_kwargs": {"enable_thinking": False}
}))
EOF

  -H "Content-Type: application/json" -d @req.json \

Verify
The OpenAI SDK with an image works unchanged against Boli; a separate test app runs the document flow end to end; credits match pages; a zero balance gets 402; the playground checked at desktop and 390px.

Stage 4 - Quality

ongoing; first round 2-4 weeks
Goal
Know, with numbers, how good Boli is per document type, and improve the weakest type.
Build
  • The full 80-150 page test set and a script that scores every model version.
  • Bake-off: Gemma 4 E4B vs 26B A4B / 31B vs Qwen3-VL-8B / 32B vs PaddleOCR-VL 1.6 (Sarvam as a reference score only).
  • Layout boxes for the preview (PaddleOCR-VL or dots.ocr as a helper) if customers ask for them.
  • If one failure type persists after a bigger model: collect or synthesise 1,000-5,000 labelled pages and LoRA fine-tune; ship as a new model name.
Verify
Before/after table per document type; no regression on the others; a public "quality" note in the docs.
The recommended approach in five lines
  1. Start with the end-to-end VLM Boli already has: Gemma 4 E4B with its mmproj on the same llama-server (Apache 2.0, no new infrastructure).
  2. Two passes per page: a faithful Markdown transcription, then fields through a JSON schema; digits, BS to AD and paisa are done in code, with cross-checks.
  3. Build a real Nepali test set early and let it choose between Gemma 4 E4B, Gemma 4 26B/31B, Qwen3-VL and PaddleOCR-VL by field accuracy, hallucinations and cost per page.
  4. PDFs: use a real text layer when present (fix Preeti), otherwise render pages on the GPU node; run every PDF as a Workflow job with R2 storage, polling and per-page credits.
  5. Fine-tune only when the test set shows a consistent failure that a bigger model and a higher image budget did not fix.
