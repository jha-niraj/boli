Boli document intelligence, chapter two

Building Boli's Document Model

How a small open vision-language model (1 to 4 billion parameters) is turned into a specialist that only reads Nepali and English documents, the way Sarvam built Sarvam Vision. This is the real-world flow, stage by stage, with numbers. No code.

Chapter one: Boli Document Intelligence (what it is, the open models, Preeti, the API)

Chapter one explained what document intelligence is and how a vision-language model reads a page. This chapter assumes that and answers the next question: once a general model is not good enough, how do teams actually make it better at one narrow job?

1. Why a specialist beats a general model

A general vision-language model (VLM: a model that takes an image plus text and writes text) is trained to do thousands of things: describe photos, answer chart questions, write code from screenshots, chat. Reading a Nepali bill is a tiny slice of what it saw in training. A specialist is the same kind of model trained further on only one job, so all of its capacity points at that job.

Our own test on 24 November 2026 showed the gap clearly. One synthetic Nepali and English bill with 54 digits on it (files in ml/docintel/):

Sarvam's 54/54 is the proof that a model of about 3 billion parameters can do this. Small is not the problem; focus is.

The core idea: narrowing the job. A specialist gives up chat, poems and photo captions. In return it reads every glyph, keeps reading order, and writes one fixed output format every time. For a document API, that trade is all upside.

Four lessons carry over to Boli:

  1. Nobody hand-writes the labels at scale. A bigger model (the teacher) writes them; humans check a sample and build the test set.
  2. Synthetic data fills the gaps. When real data is scarce (Nepali digits, Preeti, rare layouts), teams render it.
  3. Training goes in stages: first learn to read, then learn the output format, then (optionally) get rewarded for passing checks.
  4. The model is not the whole product. Sarvam and PaddleOCR both put a layout and reading-order step around the VLM.

3. The full pipeline

This is the real-world flow from idea to a model behind Boli's API. Stage 3 (data) is drawn bigger because it is where most of the time goes, in every published project.

The pipeline. Notice where the loops land: when a specialist is wrong, the fix is nearly always better or more targeted data.

3.1 Define the job and the output format

Write down, before anything else, exactly what goes in and what comes out. This sounds trivial. It is the decision that shapes every training example you will make.

  • Inputs: printed Nepali (Unicode and Preeti-era), English, and mixed pages. Document types: bills and invoices, government notices and letters, certificates, bank statements, forms, textbooks. Phone photos and scans, not just clean PDFs. Leave out handwriting for version one; it is a separate, much harder job.
  • Output, step one (Read): the whole page as typed blocks in reading order. This is what Sarvam returns: each block has a type (section-title, paragraph, list, table, footer, page-number) and tables keep their structure (thead, tbody, tfoot, numeric cells).
  • Output, step two (Extract): fields to JSON with a schema, done by a second pass as chapter one described. Keep the document model focused on reading. Extraction stays a separate, cheaper call.

A training target then looks like this (the model learns to write exactly this shape):

<h2 data-type="section-title">बिल / Invoice</h2>
<p data-type="paragraph">ग्राहकको नाम: राम बहादुर थापा</p>
<table>
  <thead><tr><th>विवरण</th><th>परिमाण</th><th>रकम (रु.)</th></tr></thead>
  <tbody><tr><td>चामल</td><td data-num>२५</td><td data-num>२,४५०</td></tr></tbody>
  <tfoot><tr><td>जम्मा</td><td></td><td data-num>२,४५०</td></tr></tfoot>
</table>
<footer data-type="footer">धन्यवाद</footer>

Why HTML-like typed blocks rather than plain Markdown? Markdown cannot say "this row is the total" or "this cell is a number", and it mangles merged cells. A small fixed set of tags is easy for a model to learn, easy to validate (does it parse?), and easy to turn into Markdown or JSON later. Two rules: copy, never correct (write the digits and spelling exactly as printed, even if the page has a typo), and never translate (Nepali stays Nepali).

3.2 Pick a base model

You almost never train a vision-language model from nothing. You start from an open one that already sees and reads, and you specialise it. Sarvam could start from their own base; we start from someone else's. What to check, in order of importance:

  1. Licence. Boli sells this. The weights must allow commercial use, and your fine-tune inherits the base licence.
  2. Runs in llama.cpp as GGUF with an mmproj file, because that is how Boli serves models today.
  3. Score on our own test set before any tuning. The best starting point is the one that already makes the fewest Nepali errors.
  4. Fine-tuning support in common tools (Hugging Face TRL, Unsloth, LLaMA-Factory). If nobody has fine-tuned it before, you will spend days on plumbing.
  5. Vision encoder and resolution handling. Devanagari has small marks above and below the line (matras, the halant). A model that sees pages at native resolution, rather than squashing them into one small square, keeps those marks.

3.3 Build the data (the biggest part)

A training example is a pair: a page image, and the exact text the model should write for it. Teams spend most of their time making these pairs. There are five sources, each covering a weakness of the others.

A starting mix, not a law. After the first evaluation you shift the shares toward whatever the model still gets wrong.

Source 1: synthetic rendering

You write a program that draws fake documents and therefore knows the exact answer for each one. Nothing needs labelling. This is how you fix the digit problem cheaply.

  • Text: real Nepali sentences from public text corpora (news, government text, Wikipedia), mixed with generated numbers, dates in Bikram Sambat (२०८३/०८/०८), money (रु. १२,३४५.००), names, addresses, PAN and phone numbers, and English words.
  • Fonts: as many as you can find (20 to 50+). Research on Hindi recognition found that more fonts helped more than more samples. Include Unicode fonts (Noto Sans Devanagari, Mukta, Kalimati, Mangal and others) and Preeti.
  • Preeti: old Nepali documents use the Preeti font, which stores Latin letters that only look Nepali. Render text in Preeti, but store the Unicode answer (converted with an open converter such as npttf2utf or the nepali-converter tool). The model then learns to read what the page shows and always write proper Unicode.
  • Layouts: templates for bills, receipts, notices, letters with letterheads, tables with totals, two-column pages, stamps and signatures overlaid. Fill the templates with random content so no two pages repeat.
  • Augmentation (making clean renders look like phone photos): blur, low resolution, JPEG artefacts, uneven lighting, shadows, slight rotation and perspective tilt, paper texture, creases, faded ink, photocopy noise. Apply it to some, not all: the model should see both clean and messy.

Volume: synthetic pages are nearly free, so make 50,000 to 200,000 and sample from them. PaddleOCR used synthesis specifically for hard cases (blurry, dense text). The risk is that synthetic pages look too tidy; that is why real pages matter.

Source 2: real public documents

Nepali government sites publish thousands of PDFs: gazette notices, circulars, budget documents, tender notices, results, forms. Textbooks and public reports add variety. These carry real fonts, real scanning noise and real layouts that a renderer will never invent.

  • Collect 2,000 to 5,000 pages across document types. Record the source URL and date for each.
  • Use only documents that are already public. Skip anything with personal data unless it is redacted.
  • Split by document, never by page: all pages of one PDF go to training or to test, never both.

Source 3: teacher labels with human checking

Real pages have no answers yet. A teacher (a bigger, slower model) writes a first draft, and people correct it. This is what olmOCR (GPT-4o as teacher), LightOnOCR (Qwen2-VL-72B) and PaddleOCR (several large VLMs) did.

  • For Boli the teacher must be open and its licence must allow using its outputs for training. Candidates: a large open VLM (Qwen3-VL 32B or bigger) on a rented GPU, combined with Tesseract's text as a hint, exactly like our hybrid. Our hybrid already got every field right on the test bill, so it is a good teacher pipeline.
  • Do not use Sarvam's API output as training labels unless their terms explicitly allow it. Most commercial APIs forbid training a competing model on their outputs. Use Sarvam only as a comparison in evaluation.
  • Automatic checks before a human looks: do Tesseract's digits match the teacher's digits? Is any text in a non-Devanagari, non-Latin script (the Bengali slip)? Does the HTML parse? Is the output suspiciously short or repeating? Pages that fail go to a person first.
  • Human check: a Nepali reader corrects the draft side by side with the image. Budget 5 to 15 minutes a page. Check all flagged pages plus a random 10% of the rest, and track how often the teacher was wrong; if more than a few percent of digits are wrong, fix the teacher pipeline before labelling more.

Source 4: targeted hard cases

After each evaluation, look at what failed and make more of exactly that. If the model still confuses १ and ९ in small table cells, render 5,000 small table cells full of ones and nines. PaddleOCR calls this hard-case mining. It is the cheapest accuracy you will ever buy.

Source 5: the human gold set

About 300 pages, fully checked by two people, covering every document type, both clean scans and phone photos, Preeti-era and Unicode, plus some English-only pages. It is frozen before training data is collected (our date-key.json idea), stored separately, and never used for training or prompt tuning. The public Nepali evaluation slice himalaya-ai/nepali-deva-ocr-eval (500 short printed snippets) can be a second, outside check.

Quality beats quantity at our scale. One thousand perfectly checked hard pages do more than fifty thousand sloppy ones, because the model learns the mistakes in its labels too.

Privacy rules for real documents

  • Train only on public documents, synthetic pages, and customer documents where the customer ticked an explicit opt-in ("help improve Boli with this document"). Default is off.
  • Redact names, citizenship numbers, PAN, phone numbers and account numbers before a human labeller sees a customer page, or replace them with synthetic values (which keeps the layout useful).
  • Keep a register: every training page has a source, a licence or consent record, and a delete path. If a customer withdraws consent, the page leaves the next training run.
  • Labellers work under a confidentiality agreement and see pages inside a tool, not as downloaded files.

3.4 Train

First, the anatomy of the model being trained. Every VLM in our comparison has three parts:

The three training stages

StageWhat the model seesWhat it must writeWhyData
A. Learn to read (continued pretraining)Text lines, crops and whole pagesPlain text, exactly as printedTeaches glyphs: digits, conjuncts, matras, Preeti. No format yetMostly synthetic, large (50K+)
B. Learn the format (supervised fine-tuning, SFT)Whole pagesTyped blocks in reading orderTeaches structure: tables, titles, footers, the "copy, never correct" ruleThe 20K to 30K mix above
C. Get rewarded for passing checks (optional)Pages with known factsIts own attempts, scoredFixes stubborn errors: reward = digits match, HTML parses, no wrong script, no repeated linesA few thousand pages with automatic checks

Sarvam ran all three (continued pretraining, SFT, then reinforcement learning with verifiable rewards). olmOCR 2 showed what stage C looks like in practice: generate small unit tests per page and reward the fraction that pass. For Boli's first version, do A and B together in one run (mix line-level reading examples into the page-level set). PaddleOCR and LightOnOCR found one well-mixed stage can match two. Add stage C only once the evaluation shows errors that more data alone does not fix.

LoRA, QLoRA or full fine-tuning

Full fine-tuningEvery weight in the model changes. Best quality (olmOCR found LoRA gave higher loss), but needs about 16 bytes of GPU memory per parameter for training state: a 4B model wants 2 to 8 large GPUs. Produces a whole new model file.
LoRA(Low-Rank Adaptation.) Freeze the original weights and train small add-on matrices, about 1% of the parameters. Fits a 4B model on one 24 to 48 GB GPU. Output is a small "adapter" file you merge back in.
QLoRALoRA on top of a 4-bit copy of the base model. Uses even less memory (a 4B model trains on a 16 to 24 GB card). Slightly lower quality and slower. Good for experiments.

The practical path: start with LoRA (rank 16 to 32, on all linear layers) because it is cheap enough to run ten times while you fix your data. Move to full fine-tuning only if LoRA stops improving on the gold set and you have 100K+ good examples.

Freeze the vision encoder, or not?

Common practice for format-only changes is to freeze the eyes and train the projector and language model. Our case is different: the digit confusion may be visual. Tools such as Unsloth let you choose separately whether LoRA touches the vision layers, the language layers, or both. Run it as an experiment: one run with vision frozen, one with LoRA on vision too, and compare digit accuracy on the gold set. If unfreezing helps digits without hurting English, keep it.

Image resolution and tiling

Each image becomes a grid of patches, and each patch becomes tokens. More pixels means sharper matras but more tokens, more memory and slower pages. Published settings: olmOCR rendered pages to 1024 px on the longest side; LightOnOCR used up to 1540 px at 200 DPI; PaddleOCR allowed much larger images in its final stage. For Nepali, aim for text height of at least 20 to 25 pixels per line after resizing. For dense pages (tables, small print), cut the page into overlapping tiles or let a layout step crop each region and read regions separately, which is what Sarvam's and PaddleOCR's harnesses do. Train at the same resolution you will serve at.

Curriculum

Order the data from easy to hard: clean single lines, then clean pages, then noisy phone photos and dense tables. In practice teams do this with mixing ratios rather than strict order: the early part of training sees more clean data, the late part more hard cases. Keep 5% English and general layout throughout so the model does not forget them.

What a run looks like

  • One epoch (one pass over the data) to three epochs. More epochs on a small set means memorising, not learning.
  • Every few hundred steps, score a 50-page slice of a validation set (separate from the gold set) and save a checkpoint. Keep the best checkpoint, not the last.
  • Watch for the two classic failures: output that repeats one line forever (a loop), and output that is fluent Nepali but not on the page (a hallucination).

Avoiding data leakage

Leakage means the test pages, or close copies of them, sneak into training. The model then looks great on the test and fails in the real world. The rules:

  • Freeze the gold set first, with a date, and keep it in a separate folder that the training scripts cannot read.
  • Split by document and by source, never by page. Two pages of the same gazette are near-duplicates.
  • Remove near-duplicates by image fingerprint (a perceptual hash) and by text overlap between training and test.
  • Hold out whole templates and whole fonts. If the test bill uses a layout or font the renderer also uses, the score is inflated. Keep 3 to 5 fonts and some templates for test only.
  • Do not tune prompts or pick checkpoints on the gold set. Use the separate validation set for that, and touch the gold set only to report.

The error-analysis loop

The single most valuable hour after each run: sort the gold pages by error, open the worst twenty, and write each failure into a category (digit confusion, conjunct split, table merged wrongly, Preeti misread, missed footer, hallucination). The biggest category decides the next batch of data. This is how PaddleOCR's hard-case mining works, done by hand at our scale.

Our test set of public Nepali documents (digital PDFs, scanned PDFs, images and synthetic degraded pages) is running now. Its results will land in ml/docintel/testset/REPORT.md and become the first version of this baseline.

3.6 Make it small and fast

  1. Merge the LoRA adapter into the base weights, giving one ordinary model.
  2. Convert to GGUF, llama.cpp's file format. A vision model becomes two files: the language model (model.gguf) and the vision side, called the mmproj (multimodal projector) file, which holds the encoder and projector.
  3. Quantise (store weights in fewer bits). The language model goes to Q4_K_M (4-bit, about a quarter of the size) or Q8_0 (8-bit, near-lossless). Keep the mmproj at F16 or Q8_0; the eyes are small and suffer most from squeezing.
  4. Re-run the whole gold set on the quantised files. Quantisation can quietly bring digit errors back. If Q4 loses more than a fraction of a point of digit accuracy, ship Q8.

Sizes for a 4B model: about 8 GB at 16-bit, about 4.3 GB at Q8, about 2.5 GB at Q4, plus a few hundred MB for the mmproj. Alternative serving: vLLM runs the unquantised model with batching and is faster per page on a big GPU when traffic is high. llama.cpp is simpler and runs on smaller machines. Start with llama-server; move to vLLM only if throughput becomes the bottleneck.

3.7 Deploy behind Boli's API

Chapter one proposed /v1/documents as a job API. The document model slots into it:

  • The API stores the job and the file, returns a job id, and a background workflow does the work. Pages take seconds each, and a 10-page PDF must survive a closed tab, so this is a long job, not an inline call.
  • The workflow splits the PDF into page images, sends each to the GPU server running llama-server with the model and mmproj, collects typed blocks, then runs the Extract pass if fields were asked for.
  • Usage is metered per page. Record model version on every result so a bad release can be traced.
  • Release safely: run the new model on a share of traffic (or alongside the old one, results hidden) for a week, compare automatic checks, then switch. Keep the previous model files for a one-command rollback.
  • Keep the hybrid as a fallback: if the model's output fails a check (digits disagree with Tesseract, script slip, unparseable HTML), rerun that page through the hybrid and flag it.

3.8 The improve loop

A shipped model is version one. The model gets better from real failures, gathered carefully:

  • Failures come from three places: automatic flags (the fallback fired), customer corrections in the playground, and support reports.
  • Only pages with opt-in consent enter the training pool. Redact first.
  • Label the failures (teacher draft plus human fix), add them to the hard-case set, render synthetic look-alikes of each new failure type.
  • Retrain on a schedule (monthly at first). A new version ships only if it beats the current one on the gold set and does not get worse on any category (the regression gate).
  • Add a few new pages to the gold set each quarter so it keeps resembling real traffic. Version the gold set; compare models only on the same version.

  • Collect 3,000 to 7,500 public pages; label with an open teacher plus the hybrid; auto-check; human-fix flagged pages and a 10% sample.

Done when: the gold set is frozen, the scoreboard has a row for every reference model, and about 25K training pairs exist.

Phase 2. First LoRA on a 2 to 4B base

1 to 2 weeksCompute $150 to $400
  • Rent one H100 or A100 by the hour. Train LoRA (rank 16 to 32) on the bake-off winner with the mixed set (reading examples plus page-to-blocks), 1 to 2 epochs.
  • Two variants: vision layers frozen, and LoRA on vision layers too. Compare digits.
  • After each run: score on the validation set (never the gold set), error analysis, then hard-case data for the biggest failure category. Expect 5 to 10 runs.

Done when: a checkpoint beats the base model clearly and stops improving between runs.

Phase 3. Evaluate against Tesseract, the hybrid and Sarvam

1 weekCompute under $20
  • Run the best checkpoint, quantised the way we will ship it, over the gold set once.
  • Go if: digit accuracy at least Tesseract's, field accuracy at least the hybrid's, zero script slips and loops, under about 5 s per page on the target GPU.
  • No-go is a fine outcome: keep the hybrid, and the data and gold set we built still pay off for the next attempt (full fine-tune, a different base, or stage C reward tuning).

Phase 4. Ship as GGUF on llama-server

1 to 2 weeksServing ~$250 to $600 a month for one always-on 24 GB GPU
  • Merge, convert to GGUF plus mmproj, quantise, re-score. Serve with llama-server on one GPU box behind the /v1/documents workflow.
  • Shadow mode for a week (new model runs, the hybrid's answer is returned), then switch with the hybrid as automatic fallback.
  • Turn on the consent checkbox and the failure queue. Start the monthly retrain.
The plan in one line: ship the hybrid now, spend most effort on a frozen gold set and a Nepali data factory, then a cheap LoRA on an Apache-licensed 4B model, and only replace the hybrid when the numbers say so.

5. What is hard, and what can go wrong

  • The teacher's mistakes become the student's. If labels have wrong digits, the model learns wrong digits. Measure the teacher's error rate on the gold set before labelling thousands of pages.
  • Synthetic pages are too clean. A model trained mostly on renders can fail on a crumpled photo. Keep real pages at 30% or more and use heavy augmentation.
  • Catastrophic forgetting. Fine-tune only on Nepali and English reading suffers, or the model forgets tables. The keep-alive slice and per-category scores catch this.
  • Fluent hallucination is worse than garbled text. Tesseract's garbled word is obviously wrong; a VLM's invented but plausible Nepali sentence is not. This is why the digit cross-check against Tesseract stays in production.
  • LoRA may not reach the eyes. If the digit confusion is in the vision encoder and LoRA with frozen vision does not fix it, you need vision-layer LoRA or a full fine-tune, which costs more.
  • Quantisation undoes gains. Always score the exact files you ship.
  • Licence and terms traps. A research-only base, a dataset with no licence, or labels copied from a commercial API can each block a commercial product later. Keep the register.
  • Privacy. One leaked customer citizenship card in a training set is a serious incident. Opt-in only, redact first, keep a delete path.
  • Long and dense pages. A full bank statement page can exceed the context window or slow the model to a crawl. Plan for tiling or a layout step that reads regions separately.
  • Benchmarks you did not build. Published scores (including Sarvam's and PaddleOCR's) are mostly on the authors' own test sets. Only our gold set says how a model does on our documents.

6. Glossary

VLMVision-language model: takes images and text in, writes text out.
Base modelThe existing open model you start from and specialise.
Fine-tuningFurther training of an existing model on examples of one job.
Continued pretrainingMore broad training on raw material (here: plain reading of text images) before teaching a format.
SFTSupervised fine-tuning: training on input and correct-output pairs.
RLVRReinforcement learning with verifiable rewards: the model tries, an automatic check scores it, good attempts are reinforced.
GRPOA popular RL method that compares several attempts at the same input and favours the better ones. Used by olmOCR 2.
LoRA / QLoRATrain small add-on matrices instead of all weights; QLoRA does it over a 4-bit base.
AdapterThe small file LoRA produces, merged into the base for serving.
EpochOne full pass over the training data.
CheckpointA saved copy of the model at a point in training.
Teacher / studentA bigger model labels data (teacher); the small model learns from it (student). Also called distillation.
Synthetic dataDocuments generated by a program, so the right answer is known.
AugmentationDeliberately degrading images (blur, tilt, shadow) so the model copes with real photos.
Hard-case miningFinding what the model gets wrong and making more training data of that kind.
Gold setHuman-checked test pages, frozen and never trained on.
Validation setA separate slice used during training to pick checkpoints, so the gold set stays untouched.
Data leakageTest pages, or near-copies, reaching training. Inflates scores.
CER / WERCharacter and word error rates: share of characters or words wrong.
TEDSTree edit distance similarity: how close a table's structure and contents are to the truth.
Catastrophic forgettingLosing old skills while learning a new one.
QuantisationStoring weights in fewer bits (8 or 4) to shrink and speed up a model.
GGUF / mmprojllama.cpp's model file format; mmproj is the separate file with the vision encoder and projector.
PreetiLegacy Nepali font that stores Latin letters drawn as Devanagari. Must be converted to Unicode.
Typed blocksOutput where each piece of the page is tagged with what it is (title, paragraph, table, footer).
Regression gateA rule that a new model ships only if it is no worse on any tracked category.
