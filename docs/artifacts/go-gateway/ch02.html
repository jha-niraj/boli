CHAPTER 02 - PRIMER

Modules, packages and visibility

How Go code is organised: a module is the project, a package is a folder, and a capital letter decides what other packages can see.

go.modcmd/gatewayinternal/boli

Module: the project

A module is a tree of Go code with a go.mod at its root, roughly a package.json. Line 1 is the module path: the prefix of every import path inside it. It is a name, not a URL Go has to fetch, but the convention is a domain you control, so bolihq.com/gateway can never collide with anyone else's code. The go line is the minimum Go version the code needs.

When pgx arrives (Chapter 8), go get adds a require line here and creates go.sum: a checksum for every downloaded file, which plays the role of pnpm-lock's integrity hashes. Both files are committed.

Package: one folder

A package is all the .go files in ONE folder. They share one namespace: a function in boli.go can call a function in another file of the same folder with no import. Every file in the folder starts with the same package name. The one exception is test files, which may use <name>_test (see below).

The import path of a package is the module path plus the folder: internal/boli becomes bolihq.com/gateway/internal/boli. In code you then refer to it by its package name, the last word: boli.CostMicro.

gofmt groups imports with standard library first, then a blank line, then everything else. Third-party paths look like github.com/jackc/pgx/v5: the /v5 is part of the path, because in Go a new MAJOR version is a different import path, so v4 and v5 can even live in one program.

Exported means Capitalised

Go has no export keyword and no public/private. The rule is one character: a name that starts with a capital letter is exported (visible to other packages), and a lowercase name is private to its package. This applies to functions, types, constants, variables, struct fields and methods.

Struct fields follow the same rule, and this matters a lot in the next chapter: encoding/json lives in another package, so it can only read and write CAPITALISED fields. A lowercase field is silently left out of the JSON.

cmd/ and internal/

Two folder names carry meaning:

  • cmd/<name>/ is a convention: each folder under cmd is one program (package main). go build ./cmd/gateway makes a binary named gateway. A second tool (say, a key-hash checker) would be cmd/keycheck.
  • internal/ is enforced by the compiler: a package under internal/ can only be imported by code inside the folder that CONTAINS internal. Our bolihq.com/gateway/internal/boli is importable from anywhere in apps/gateway-go and from nowhere else. This is how you say "not a public API" in Go.

Here is where the service is heading. Only cmd/gateway and internal/boli exist today; the rest lands chapter by chapter.

Dependencies point one way

Go forbids import cycles. If a imports b and b imports a, nothing compiles:

TypeScript tolerates cycles (sometimes with a confusing undefined at load time). Go makes you decide which package is lower-level. The usual fix is to move the shared piece into a third, lower package, or to have the lower package declare an interface that the upper one satisfies (Chapter 5).

Test files and the two test packages

A file ending in _test.go is compiled only by go test, never into the binary. boli_test.go says package boli, so it is a white-box test: it can see lowercase names. A test file may instead say package boli_test: a black-box test that must import bolihq.com/gateway/internal/boli and can only use exported names, exactly like a real caller. We use white-box for small pure packages and black-box for the HTTP API.

Package-level state: keep it to config

var Models = []Model{BoliChat} is a package-level variable: created once when the program starts, shared by everything. Fine for fixed tables. For anything that changes at run time (a database pool, a counter), package-level variables become hidden global state that tests can't swap out. The service keeps them for read-only tables, and passes everything else explicitly as struct fields, starting in Chapter 5. Go also has func init(), which runs automatically before main. We avoid it, because code that runs implicitly is hard to follow.

Traps

  1. Private is per PACKAGE, not per file. A lowercase name in boli.go is visible in every other file of internal/boli. Split a package only when you want a real boundary.
  2. Two package names in one folder do not compile (the only exception is x_test in test files). One folder, one package.
  3. The package name is what you type, the path is what you import. They usually match the last path element. When they do not, such as pgx's path ending /v5 while its package is named pgx, you still type pgx.Connect.
  4. A lowercase struct field is invisible to encoding/json. No error, it just is not in the output. Chapter 3 starts here.
  5. Do not name a package utils, common or helpers. The name is part of every call (utils.Do says nothing). Name it by what it provides: apierr.Write, store.Charge.
  6. Importing a package runs its package-level initialisers (and any init()). Keep them cheap and free of I/O, so importing never connects to a database.
  7. The import path must start with the module path in go.mod. Rename the module and every import changes with it.
